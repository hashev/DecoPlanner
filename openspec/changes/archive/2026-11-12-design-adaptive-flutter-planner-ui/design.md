# Design

## Context

Мотивация и границы изменения — в `proposal.md`. Flutter-проекта и `pubspec.yaml` в репозитории нет. Доступны извлечённые FXML/CSS, декомпилированные контроллеры и выполненные численные эталоны. Текущий анализ интерфейса статический: окно оригинала в этом изменении не запускалось, визуальное совпадение не проверено.

Опорные источники относительно корня репозитория:

## Goals / Non-Goals

**Goals:** обеспечить прослеживаемость каждой функции и проектировать целевые взаимодействия, не перенося ошибки исходного UI. Создать дизайн-пакет, по которому можно отдельно поставить реализацию Flutter без повторного исследования навигации и состава экранов.

**Non-Goals:** пиксельное копирование JavaFX, копирование фирменного оформления GUE, реализация ядра, исполняемый прототип, облако, аккаунты, журнал реальных погружений, синхронизация и новые алгоритмы резервов. Дизайн не подтверждает пригодность численных примеров для планирования реальных погружений.

## Decisions

### 1. Результат apply — проверяемый комплект дизайна

Создать `docs/ui/README.md`, `legacy-interface.md`, `feature-map.json`, `flows.md`, `design-system.md`, `screens.md`, `flutter-handoff.md`, `review.md` и каталог `mockups/` с SVG и растровыми превью. Каждый макет имеет ID, связанные требования, сценарий, размер, тему, состояние и происхождение чисел. Реестр содержит `id`, исходный ресурс/символ, поле/действие, доказательство и его статус, целевой экран/компонент, макет, решение по включению/исключению.

Альтернатива — сразу создавать Flutter-shell с фиктивным расчётом — смешивает проектирование с реализацией и создаёт ложное ощущение готовности ядра. Она отложена в отдельное изменение. Эти спецификации — целевой UI-контракт; завершение apply означает готовность дизайна, не выполнение требований работающим приложением.

### 2. Покрытие организовано вокруг задач пользователя

Основная навигация: **План · Инструменты · Настройки**. Результаты принадлежат выбранному погружению внутри «Плана», а не глобальной вкладке без контекста. Справка доступна в контексте поля и из настроек; базовые определения доступны офлайн. Внешняя документация открывается явным действием. Стартового маркетингового экрана нет.

| Целевой экран | Функции оригинала / границы |
|---|---|
| P01 План / последовательность | Выбор погружения, добавление следующего, интервал, OC/CCR, связь с предыдущим состоянием, сброс с подтверждением. |
| P02 Уровни | Глубина, длительность, O2/He; CCR — setpoint/дилюент; перестановка, добавление, удаление. |
| P03 Газы | Наборы, переключения, потеря газа, минимальная остановка; CCR — дилюент/setpoint. Неприменимые параметры не выдаются за работающие. |
| P04 Результат | Таблица и сводка runtime/ascent/deco/off-gassing, CNS/OTU, GF, состав; плотность там, где даёт соответствующий режим. |
| P05 Анализ | Профиль, только подъём, сохранённые сравнения, графики тканей N2/He/M-values, ratios и группы остановок. |
| P06 Газовый расход | Расход на одного дайвера без резервов, размер баллона, требуемое давление. |
| P07 Bailout | Связанный сценарий из CCR, точка перехода, CCR/OC-сегменты, собственные газы/расход/результаты. |
| P08 Таблицы диапазонов | Диапазоны глубины/времени, варианты без декогаза / переключений, результат и печатный вид. |
| T01–T07 Инструменты | MOD/END, плотность, подбор смеси, смешивание, дозаправка, уравнивание, конверсия баллонов. |
| T08 Объём и стоимость | Рецепт T04, баллон, цены O2/He, доплата дозаправки, итог. |
| S01 Параметры плана | Модель/GF/консерватизм, скорости, последний стоп, минимум, длительность со спуском, RMV/OCR/low setpoint, высота/акклиматизация. |
| S02 Справочники и вид | Наборы декогазов, баллоны, единицы, light/dark, графики и очистка сравнений. |

Альтернатива — воспроизвести множество вкладок JavaFX — сохраняет состав полей, но делает ввод и результаты труднодоступными на телефоне. В новом реестре у каждого legacy-поля будет точная целевая привязка, а не только эта обзорная таблица.

Лицензионные уровни Rec/Tech и их ограничения в исходных проверках маркируются как лицензирование, не как физиологические пределы. Они не переносятся автоматически в валидацию собственного продукта. Ограничения исходного алгоритма и недоступные ветви отражаются отдельно в техническом handoff.

### 3. Адаптация по ширине окна, одна модель состояния

Использовать подход official skills `flutter-build-responsive-layout` и `flutter-apply-architecture-best-practices`: `LayoutBuilder` для доступного места, общие состояния и разные представления. Не определять тип устройства и не блокировать ориентацию.

| Ширина, logical px | Структура |
|---|---|
| <600 | `NavigationBar`; в «Плане» выбор погружения и локальные разделы «Ввод / Газы / Результат»; редактирование уровня на отдельном экране. Графики/расход/таблицы открываются из результата. |
| 600–999 | `NavigationRail`; основная панель и последовательный переход к деталям; форма до 640 px, результаты занимают доступную ширину. |
| ≥1000 | Rail 88 px, редактор 340–420 px, результат от 480 px, зазор 16 px; дополнительные параметры в панели/диалоге. При нехватке места вернуться к средней компоновке. |

Состояние не создаётся заново при смене breakpoint; сохраняются черновик, выбранное погружение/раздел, открываемый объект и позиция просмотра. Увеличенный текст может раньше включить последовательную компоновку. Desktop-плотность не уменьшает область нажатия кнопок. Сложные таблицы на телефоне заменяются списками раскрываемых остановок; двумерная range-таблица имеет также список результатов, а не обязательный горизонтальный скролл всей страницы.

### 4. Состояния и ввод являются частью дизайна

В `flows.md` зафиксировать переходы `empty → draft → invalid/calculating → ready/error`, `ready → stale` при изменении расчётных входов и отдельное `unavailable`. В `calculating` повторный запуск блокируется; уход со страницы не теряет ввод. Результат содержит revision входов; устаревший ответ игнорируется. Изменение раннего погружения инвалидирует зависимые расчёты и bailout. Тема, раскрытие строки и масштаб графика revision не меняют.

Ввод: постоянные подписи, единицы рядом с числом, десятичная клавиатура, разделитель `,` или `.`, без разделителей тысяч; неоднозначные смешанные разделители отклоняются. O2 и He вводятся в %, N2 — вычисляемое поле; хранение долей определено расчётным контрактом. Не запрещать промежуточное пустое значение во время редактирования. Полный submit проверяет все поля и переводит фокус на сводку ошибок с переходами к полям; ошибки также остаются inline. Не заменять ошибку молчаливым ограничением числа.

Смена единиц преобразует физическое значение, а не переподписывает введённое число. Невалидный незавершённый ввод сначала исправляется или отменяется пользователем; данные не теряются. Исходное значение хранится без повторного округления на каждом переключении. Смена режима с несовместимыми уровнями, сброс плана и удаление погружения с зависимостями показывают последствия перед подтверждением. Отмена сохраняет черновик. Сохранять набор газов, сохранить параметры по умолчанию и применить параметры текущего плана — различимые действия.

### 5. Спокойная инструментальная дизайн-система

Выполнен поиск `ui-ux-pro-max`: `technical planning data dashboard --design-system`, уточнение `scientific dashboard --design-system`, Flutter `adaptive forms keyboard` → уточнение `form`, UX `error summary validation`. Генератор предложил пригодные Minimalism & Swiss Style и Fira Sans/Fira Code, но оба шаблона страниц оказались маркетинговыми (Enterprise Gateway / Minimal Single Column). Шаблоны и GSAP/scroll reveal отклонены как неподходящие. Проверенные совпадения Flutter Forms и ошибок используются как рекомендации; web ARIA заменяется Flutter Semantics/Focus, не копируется буквально. Версию SDK из базы skill не считать выбором SDK проекта.

Выбор: непрозрачные поверхности, строгая сетка, один основной action, слабая декоративная нагрузка. Альтернатива — «подводное» оформление с фоном/градиентами/glass — ухудшает чтение плотных чисел. Не использовать изображения, старые растровые иконки или бренд оригинала.

Стартовые токены для макетов (контраст всех сочетаний проверить в apply):

| Роль | Light | Dark |
|---|---|---|
| background / surface | `#F8FAFC` / `#FFFFFF` | `#0F172A` / `#1E293B` |
| text / secondary | `#0F172A` / `#475569` | `#F8FAFC` / `#CBD5E1` |
| primary / onPrimary | `#1E40AF` / `#FFFFFF` | `#93C5FD` / `#0F172A` |
| warning text | `#92400E` | `#FCD34D` |
| error text | `#B91C1C` | `#FCA5A5` |
| success text | `#166534` | `#86EFAC` |

Роли warning/error/success всегда имеют текст/иконку; состав смеси обозначается O2/He, не только цветом. Цвет газа не является обещанием его допустимости. Отдельно определить focus/control-border/chart tokens по результату замера 3:1 для значимых границ и линий.

Типографика: Fira Sans с кириллицей, Fira Code для избранных численных сводок; основной текст 16, подписи не меньше 14, заголовки 20/24/28 logical px; tabular figures в таблицах. Шрифты при будущей реализации поставляются локально с лицензиями, без сетевой загрузки. Шаги отступов 4/8/12/16/24/32, радиусы 8/12; единый набор Material Symbols outlined, иконка 24, hit area ≥48. Цифры выравниваются по разрядам, единицы показываются в заголовках и доступных именах.

Реакция на нажатие — немедленная смена состояния; необязательный feedback 80–150 ms, переходы экранов около 200 ms. Reduced motion убирает необязательные перемещения, без задержки данных. Полный keyboard focus, safe areas, высота клавиатуры и масштаб текста входят в аннотации макетов.

### 6. Графики и данные не теряют смысл на телефоне

Профиль: время слева направо, глубина вниз от нулевой поверхности, подписи осей и единиц; газовые переключения и setpoint отмечены текстовыми маркерами. Hover и touch выбирают одинаковую точку; доступен табличный эквивалент. Сравнения показывают легенду с именем плана, моделью, входами и актуальностью, различаются также штрихом/маркером. Применимые графики тканей показывают выбранную ткань/газ, единицы и опорные линии; не подменять давление глубиной без подписи.

Карточка остановки на телефоне показывает глубину, длительность, runtime и газ; раскрытие содержит остальные столбцы режима (PO2, GF, CNS, OTU, расход; CCR — дилюент, эффективный газ, плотность). Детали не прячутся только в tooltip. Ratios подписываются как округлённая сводка и не заменяют таблицу остановок. Различать total runtime, ascent time и deco time — оригинал хранит их отдельно.

Печатный вид: белый фон, чёрный текст, подписи без зависимости от цвета, выбранное погружение, параметры модели, единицы и входы. Desktop — preview/печать, mobile — preview и системное действие печати/сохранения/поделиться при доступности. Отмена или недоступный platform action сохраняют preview и исходный результат. Реализация экспорта и формат файла выбираются отдельным изменением, здесь фиксируются содержимое и состояния.

### 7. Flutter handoff без зависимости от JVM

В handoff сопоставить экраны с `Scaffold`, `NavigationBar`/`NavigationRail`, `LayoutBuilder`, `Form`/`TextFormField`, ленивыми списками, desktop-таблицей, `FocusTraversalGroup`, `Shortcuts`/`Actions` и `Semantics`. Графики описать через необходимые interactions/accessibility, не выбирать пакет до реализации. Для простых состояний достаточно View/ViewModel с immutable snapshots и constructor injection; никаких новых state-management/DI/codegen-зависимостей в этом изменении.

Presentation отвечает за ввод, фокус и отображение; слой состояния — за черновики, revision и инвалидирование; вычислительная граница принимает смысловой запрос из `docs/calculations/contract.md`, возвращает результат/ошибку/capabilities. Java-глобалы и обфусцированные имена не попадают в UI. Расчётные задачи не блокируют поток интерфейса; механизм изоляции выбирается при переносе ядра. Предусмотреть недоступность ветвей ядра, но не добавлять fallback с выдуманными числами.

Desktop: Tab/Shift+Tab, Enter для подтверждения формы, Escape для отмены диалога, Command+Enter на macOS / Ctrl+Enter на Windows для расчёта в контексте плана. Delete/Backspace внутри поля не удаляет строку. Все shortcuts имеют видимые альтернативы. Mobile: системное «назад», безопасное закрытие редактирования, scroll-to-field при клавиатуре. Системная рамка и оконные кнопки остаются платформенными.

### 8. Критерии готовности макетов

Матрица: 375×812 и 390×844 portrait, 844×390 landscape, 768×1024, 1024×768 и 1440×900; дополнительно точные переходы 599/600 и 999/1000 по ширине. Это тестовые размеры, не фиксированные размеры приложения. На 375/1440 — ключевые экраны в обеих темах; на остальных — проверка структуры и текста. Увеличенный текст 200% и самый большой доступный размер при будущей runtime-проверке; пользовательские настройки уменьшения движения и ошибки/пустые состояния документированы.

Визуально оформить P01–P08, T01–T08, S01–S02 на мобильном и desktop; для повторяющихся инструментов разрешён общий шаблон с отдельным заполненным макетом каждого набора полей. Для среднего размера достаточно аннотированного адаптивного варианта. Обязательные состояния: исходный/заполненный ввод, раскрытая остановка, stale, calculating, field errors, failed/unavailable, reset confirmation и сравнение профилей.

SVG открыть/отрендерить и проверить превью: отсутствие обрезки, наложений и потери подписей; отчёт содержит размеры, проверенные темы, контраст и нерешённые замечания. Статические макеты не доказывают управление клавиатурой, screen reader или поведение macOS/Windows. Для них handoff содержит ручные сценарии будущей runtime-проверки, а текущий отчёт честно помечает их «не выполнялось». Численные примеры берутся из существующих fixtures с ID; прочие заполнения помечены как иллюстрация.

## Risks / Trade-offs

- [FXML не охватывает динамические диалоги] → дополнить реестр конкретными обработчиками W/R/Y и состояниями из контроллеров; непроверенные визуальные свойства обозначать явно.
- [Плотность desktop и полнота mobile конфликтуют] → компактная сводка с раскрытием всех полей; ни одна функция не исключается только из-за ширины.
- [Исходные VPM/высота/SI и кислородные ветви имеют дефекты] → дизайн ошибок/capabilities; не копировать дефекты как успешные результаты и не исправлять алгоритмы в UI.
- [Слишком много форм в настройках] → параметры текущего плана и справочники разделены; расширенные настройки раскрываются по месту, применимые значения видны в сводке.
- [Неподтверждённое поведение печати/графиков] → целевые interactions фиксируются как проектные решения, а не наблюдавшиеся свойства оригинала.
- [Дизайн ошибочно принимают за готовое приложение] → отдельные статусы UX и ядра, происхождение демонстрационных данных, отсутствие исполняемого прототипа в deliverables.

## Migration Plan

Миграции приложения нет. Apply добавляет только `docs/ui/`; оригинал и расчётный пакет доступны независимо. После проверки покрытия и макетов создать отдельное предложение реализации Flutter UI и отдельный план переноса ядра, используя этот handoff. Откат дизайна — удаление только добавленного пакета без изменения исходных данных.
