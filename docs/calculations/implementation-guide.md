# Как использовать материалы для своего планера

**Исследовательский пакет готов для проектирования и проверки отдельных частей.
Полностью проверенным эквивалентом DecoPlanner он не является.** Особенно нельзя
считать исходный VPM OC эталоном успешных высотных/повторных расчётов: он падает.

## Что брать из пакета

1. `analysis/manifest.json` идентифицирует исследованную сборку.
2. `analysis/coefficients/` содержит извлечённые таблицы, а не пересказ из литературы.
3. `docs/calculations/` описывает формулы, порядок вычислений, состояния и ошибки.
4. `analysis/fixtures/requests` + `results` — пары переносимых JSON. `actual` —
   результат оригинального байткода, не вычисление автора исследования.
5. `analysis/bytecode/symbols.json`, `maps/field-accesses.json`, `engines.json` —
   трассировка из смыслового описания обратно в исходный символ.
6. `analysis/reports/coverage.json` показывает, где проверен результат, где
   воспроизведено исключение и какие ветви/представления ещё не проверены.

Для математического переноса достаточно контракта и тематических документов.
Байткод нужен, когда возникает расхождение или приходится расширять покрытие;
декомпиляция остаётся доказательным материалом и не является готовой библиотекой.

## Рекомендуемые границы нового ядра

Следующее — рекомендации для будущего проекта, а не скрыто добавленная реализация.

```text
input validation --> unit conversion --> explicit initial state
                                             |
profile levels --> segment builder --> tissue propagation
                                             |
                           model-specific ceiling and search
                                             |
                      stops + gas/setpoint transitions
                                             |
            tissue snapshots + oxygen load + gas usage
                                             |
                   presentation rounding / export / chart
```

Хранить внутри один согласованный набор единиц давления и времени; legacy
pressure-depth/ATA/bar-конверсии оформить как явный адаптер совместимости.
Коэффициенты, настройки и начальное состояние передаются аргументами. Не
переносить глобальные O и static-state как архитектуру будущего приложения.

Модель растворённых газов — общий слой Haldane/Schreiner; допустимый потолок
и состояние VPM — отдельный слой. Построитель остановок получает функции
propagate/ceiling/transition, но различия OC/CCR/Bühlmann/VPM сохраняются до
доказательства эквивалентности. Расход, CNS/OTU и таблицы не должны менять
расписание через форматирование пустых строк.

## Порядок реализации

- Сначала структуры, единицы, точные коэффициенты и чистые Haldane/Schreiner.
  Проверить 16 тканей по постоянной глубине и линейному спуску.
- Затем Bühlmann mixed a/b, GF ceiling и поиск первой остановки. Использовать
  независимые synthetic tissue cases `ceiling-*`, включая B/C и GF0/1.
- Затем полный OC-профиль с газовыми переключениями, точным различием raw/display
  runtime. Сверить stops, tissues, CNS/OTU и gas usage, не только total time.
- Добавить CCR и bailout раздельно, затем высоту и повторные погружения.
- VPM реализовать через explicit bubble state и его преобразования; сначала
  нормальные c0..c4, затем тщательно решить дефекты legacy-высоты/повторных dive.
- Вспомогательные калькуляторы смешивания, density/MOD/END и стоимость можно
  реализовать независимо; reserve model потребует отдельного проектирования.
- UI, графики, HTML и печать строить после стабильного численного контракта.

Язык, UI framework и платформа здесь не выбраны: данные не завязаны на JavaFX.

## Сквозной проверенный пример без чтения Java

Запрос `oc-air-30m-20min`: metric, Bühlmann B, OC, air21/0, level30m/20min;
спуск10,подъём9,step3,min-stop1,GF30/85,includeTravel=true,RMV20/15,
surface10.1325,vapor.627. Surface setter задаёт N2=(10.1325-.627)*.79=7.509345.

1. Создать descent 0→30m за3мин и hold30m за17мин. He=0.
2. Для первого компартмента half=5,k=ln2/5. Schreiner с Pi0=7.509345,
   R=7.9,dt=3 даёт N2=11.819929390780718.
3. Haldane с Pinspired=(30+10.1325-.627)*.79 иdt17 даёт N2=
   29.37254134663444. Остальные15 тканей считаются теми же формулами со своими k.
4. Взять a/b из таблицы B. При GF=.3 максимальный ceilingDepth=
   10.761968793489395, ведущий compartment1. Начало off-gassing=
   18.81561309814453 по исходному root search. Округление candidate даёт12m.
5. Наклон GF=(.85-.3)/(-12)=-.04583333333333334. Для следующей9m глубины
   применяется GF=.4375. Пробные выдержки считаются на сохранённых тканях,
   пока округлённый потолок не разрешает переход.

| Depth | Отображаемая duration | Start | End |
|---:|---:|---:|---:|
| 30 | 20 (включает спуск) | 3 | 20 |
| 12 | 1 | 22 | 23 |
| 9 | 1 | 23 | 24 |
| 6 | 1 | 24 | 25 |
| 3 | 2 | 25 | 27 |
| 0 | 0 | 28 | 0 (специальная строка) |

Столбцы — исходное отображение, а не равенство End-Start=duration во всех
строках. Движения находятся отдельно в result.n. Последний сегмент физически
заканчивается на runtime27.333333333333332, а original table rounds runtime=28.
Сумма расхода1719.4744633604735L, после UI-rounding1719L, для2x12L —72bar.
Конечный CNS=.050839995582775674, OTU=13.38762401339048. Все конечные ткани
и промежуточные состояния находятся в JSON; проверять весь массив, а не одну ткань.

Это достаточно конкретный пример, чтобы собрать минимальный расчёт на другом
языке и установить первую регрессию. Затем прогнать остальные случаи той же моделью.

## Что переносить как факт, а что решать отдельно

Факты legacy: таблицы, pressure constants, порядок газов, GF-интерполяция,
различные округления, целочисленные часы CNS, включённые концы SI-циклов,
ANY-критерий critical volume, отбрасываемый результат projected ascent,
различия high-PO2 ветвей. Всё это документировано и не исправлено в оригинале.

Решения нового проекта: устранять ли каждую ошибку; какое отклонение от legacy
допустимо; какие дополнительные эталоны принять; как рассчитывать резервы;
какие входы считать допустимыми. Исправленное поведение получает новые тесты,
а legacy fixtures остаются с исходным результатом/исключением и явной пометкой.
Не переписывать эталон под новый код ради зелёной проверки.

Для VPM persistent state хранить radii/crushing/gradients наряду с тканями,
если этого требует выбранная исправленная модель. Оригинальный контроллер
сбрасывает часть этих полей до surface interval; его режим воспроизведения
должен отдельно сохранять такой порядок. Один массив N2/He не является
универсальным полным состоянием любой VPM-реализации.

## Проверка новой реализации

Новый адаптер должен выдавать тот же машинно-читаемый смысл: segments, остановки,
газы/setpoint, ткани, CNS/OTU, raw и displayed times. Сравнивать по правилам
`dp-reference-v1` либо заранее согласованным допускам для другого языка.
Для целых минут, списка остановок и выбора газа сравнение точное. Численная
близость total time не компенсирует разную структуру профиля.

Матрица исходных ошибок — отрицательный эталон, а не список разрешённых ошибок
нового планера. Успешные замены этих ветвей требуют независимых данных.
Исчерпывающая проверка безопасности реальных погружений не выполнена этим
исследованием и не следует из совпадения с поставленной сборкой.
