# Проверка относительно оригинального ядра

Нормальные расчёты выполняются без окна, на оригинальных классах `dp.jar`.
Адаптер не использует восстановленный CFR-код как исполняемый эталон.
Зависимости OpenJFX 17.0.2 (`base`, `graphics`, `controls`, `fxml`, `media`, `web`, mac-aarch64)
взяты с Maven Central; URL и SHA-256 каждого файла —
lock.json (локально: `../../local/reference/analysis/dependencies/javafx/lock.json`). Нативные Windows-библиотеки
поставки не используются. Все Preferences подменены отдельной in-memory factory;
это изоляция хранилища, а не замена вычислений.

## Повторить один пример

Из корня проекта:

```sh
python3 analysis/tools/fetch_javafx.py
python3 analysis/tools/runner.py analysis/fixtures/requests/oc-air-30m-20min.json --output /tmp/decoplanner-result-new.json
```

Выходной JSON должен отсутствовать. Новый каталог сборки можно указать через
`--build /tmp/decoplanner-build-new`. Адаптер пересобирается, если хеш Java-исходников
не совпадает с маркером сборки. Это сборка только адаптера, не приложения.
Исходные артефакты сохраняются; `manifest.py --verify` проверяет 205 файлов поставки.

## Формат входа

```json
{
  "id": "example",
  "model": "b",
  "mode": "oc",
  "units": "metric",
  "levels": [[30, 20, 21, 0, 0]],
  "deco": [[6, 100, 0, 0, 1]],
  "settings": {"gf_low": 0.3, "gf_high": 0.85, "min_stop": 1}
}
```

Уровень: `[depth,duration,O2%,He%,setpoint]`; глубина и время в выбранных единицах
и минутах; setpoint ATA. Газ deco: `[switchDepth,O2%,He%,setpoint,minStopOverride]`,
последние два необязательны. `model`: b/c/vpm; `mode`: oc/ccr/bailout.
Для последовательности: `dives: [levels1,levels2,...]`, `intervals: [60,...]`.
Допустимые имена настроек — `SETTINGS` в runner.py (локально: `../../local/reference/analysis/tools/runner.py`).

`op=scalar` позволяет вызвать оригинальную формулу по `class`, `method`,
`signature` (`double`/`int`) и `values`. `op=constants` выгружает static-константы
и массивы выбранного класса после подготовки модели. Reflection нужен из-за
обфускации и private методов; вычисления не заменяются.

## Что сохраняется

Результат содержит исходный запрос, хеш JAR, хеш исходников адаптера, JDK,
зависимости, фактические static-настройки O (включая private surface/vapor/N2),
необработанные результаты и ошибки. Для плана сохраняются входной J и выходной J,
снимки тканей каждого сегмента и static-массивы ядра. Буквенные поля расшифрованы
в [state.md](state.md). NaN/Infinity обозначаются строками, а не недопустимыми
JSON-числами. Нельзя трактовать их как корректный численный ответ.

Независимые случаи запускаются в отдельных JVM. Несколько погружений одного
случая используют оригинальный M и его surface interval внутри одной JVM.
Таймаут по умолчанию 15 секунд. Ошибки JSON отклоняются до запуска; исключения
оригинала и таймауты сохраняются с отдельным `error.kind`. Если ошибка возникает
при построении Alert, это ограничение безоконного выполнения конкретной ветви,
а не доказательство правильного сообщения или поведения UI.

## Соглашения и ограничения адаптера

Подготовка сегментов повторяет наблюдаемый путь W/R/Y; сам адаптер ещё должен
проверяться граничными и смешанными профилями. Контрольные данные доказывают
поведение ядра на явно подготовленных входах, а не полную эквивалентность UI.
В том числе явная установка surface pressure через `O.B(double)` пересчитывает
начальное N2. Reset O первоначально задаёт 7.5567, а setter при стандартном surface
и vapor Bühlmann даёт 7.509345. Фактические параметры записаны в `settings`;
совпадение с неявными preferences пользователя не предполагается.

Первые примеры включают поверхность, постоянную глубину, спуск и подъём с
промежуточными тканями. Проверены неправильная смесь/время/JSON, таймаут процесса
и независимость результатов от порядка запуска. Лог загрузки классов первого
нормального OC-профиля не содержит Main/P/e/B/c (запуск, лицензирование,
обновление, сетевой идентификатор).

Численные допуски для повторения на том же JDK: абсолютный 1e-9, относительный
1e-12 для необработанных double; для дискретной структуры и отображаемых полей
точное сравнение. Это допуск на вычислительный шум, не на изменение минут
остановок. Допуски должны назначаться по полям до проверки новой реализации.
Совпадение с модифицированным оригиналом не подтверждает безопасность погружения.

## Проверка набора и неизменные правила сравнения

```sh
python3 -m unittest discover -s analysis/tools/tests -v
python3 analysis/tools/verify.py --report /tmp/decoplanner-verification-new.json
```

Политика `dp-reference-v1` определена в verify.py: порядок и длина массивов,
строки, bool, int, отображаемые поля таблиц и округлённые итоги расхода сравниваются
точно; остальные raw double — abs1e-9/rel1e-12. Для OC rows raw L/N/F и CCR rows
raw A/P/H оставлены численными, остальные отображаемые поля точные. Правило
определяется путём, а не совпадением текущего числа; допуски не расширяются при
ошибке. Расхождение содержит JSON-путь, оба значения и абсолютную/относительную
ошибку для чисел.

У ошибок сравнивается тип и сообщение корневого исключения без номеров строк
адаптера. Воспроизведение известного исключения означает совпадение ошибочного
поведения, а не успешный план. `matches_reference` всегда читается вместе с
`outcome`. Операция `--refresh-metadata` разрешает перезапись только после
сравнения неизменных выходов и сигнатуры ошибки; она обновляет данные о текущем
адаптере/окружении, не принимает новые числа как эталон автоматически.

Для `op=oxygen`: values=[startDepth,endDepth,duration,O2%,He%,setpoint,rate],
phase=constant/motion. Для `op=ui` задаются class/method, необязательные
ctor_signature/ctor_values и fx (имена полей→строки). В обоих случаях выполняется
исходный метод. `postprocess=true` у плана вызывает реальные gas/ratio
контроллеры на невидимых JavaFX controls. `glass.taskbarApplication=false` и
module-path исключают ненужное создание Dock-приложения; окна не показываются.
