# Производные результаты, таблицы и единицы

## Ratios

Статус: исходные W.H(), R.A(), Y.L() выполнены через контроллеры без показа окна.
В JSON `derived.ratio_text` сохранены реальные подписи, числа и группировки.

Bottom time для OC = сумма длительностей пользовательских сегментов (C=true)
с ролью газа bottom. Для CCR — сумма всех пользовательских сегментов.
Total deco берётся из внутреннего J.E, а не просто T-bottomTime:

```text
decoMinutes = JavaRound(J.E)
percent = JavaRound(decoMinutes/bottomTime*100)
if percent == 100: ratio = 1:1
else if percent > 100: ratio = 1:roundTenth(percent/100)
else: ratio = JavaRound(100/percent):1
```

Когда округление сокращает требуемое время, UI добавляет предупреждение.
OC дополнительно считает процент времени на каждом декогазе из h.Q.
CCR группирует интервалы: первые два стопа 6m/3m (20ft/10ft) — отдельная
группа у поверхности; следующие группы по O.R (default5) стопов, с обрезкой
по максимальной глубине. Суммируются длительности table rows, а не минуты
движения сами по себе; среднее время делится на настроенное число стопов,
даже у обрезанной группы. Поэтому «среднее» может отличаться от деления на
фактически присутствующие строки.

Проверка 30m/20min OC: total deco5, percent25, rounded4:1.
CCR45m/25min: total15,60%,2:1; группы18–9m:6мин,24%,4:1,avg1.2;
6–0m:9мин,36%,3:1,avg4.5. Это численные выходы оригинала, а не рекомендации
планировать по округлённому отношению.

## Top-off, уравнивание баллонов и ёмкость

Статус: подтверждено байткодом и прямыми вызовами K.G(), K.T(), K.W().

Top-off, K.G():

```text
addedPressure=Pfinal-Pinitial  # must be >0 at UI
O2final%=roundTenth((O2initial*Pinitial+O2top*addedPressure)/Pfinal)
Hefinal%=roundTenth((Heinitial*Pinitial+Hetop*addedPressure)/Pfinal)
```

Здесь O2/He в процентах. Air50bar + EAN32 до200bar → EAN29.2 по ties-to-even.
Это идеальное смешивание; EOS Q здесь не вызывается.

Уравнивание, K.T(): `Pfinal=(P1*V1+P2*V2)/(V1+V2)`; источник реализует через
перенос количества из high в low. Imperial объёмы делятся на100, общий
множитель сокращается; учитываются номинальные введённые объёмы, не отдельная
температурная EOS. 12L/50bar и50L/200bar →171.0bar.

Конверсия metric cylinder, K.W():

```text
PSI=JavaRound(bar*14.50377)
correction=1+0.0002615*bar
litersFree=bar*waterLiters/correction
capacityCuFt=roundTenth(litersFree/28.31685)
```

Обратная K.Y(): bar=round(PSI/14.50377), correction по округлённому bar,
waterLiters=roundTenth(CuFt*28.31685/(PSI/14.50377)*correction).
Пример12L/232bar →92.7CuFt и3365PSI.
Это другая конверсия, чем простое Tank.G(); различие сохранено.

## Range tables

Статус арифметики: подтверждено исходным кодом. Полный диалог/WebView/HTML-export
не выполнялся; это явный пробел покрытия UI, не пропущенный расчётный алгоритм.
W/R/Y перебирают сетку depth и duration с включёнными границами, меняют последний
введённый уровень, заново создают J и вызывают тот же S/A/H/D. Для каждой длительности
собирается отображаемая таблица глубина→duration, суммируются целые минуты;
начальная bottom row удаляется для печати. Отдельной модели декомпрессии здесь нет.
Перед генерацией сохраняются прошлый J и M-state; после возвращаются.

Проверка новых численных вариантов возможна отдельными request JSON на узлах
сетки, что уже покрыто normal/multilevel/GF примерами. Для проверки именно
HTML-таблиц нужно вызвать интерактивный range dialog, снять экспорт и сравнить
каждую ячейку с такими JSON. Печать и оформление не нужны вычислительному ядру.

## Tissue graphs

Статус: snapshots и формулы подтверждены; отрисовка графиков не выполнялась.
W/R/Y читают d.T/K и строят total tissue pressure, ambient и M-values.
На постоянных сегментах >1.5min вставляются промежуточные точки Haldane с шагом
1 минута; конечные точки берутся из сохранённых тканей. M-value вычисляется
через уже описанные weighted a/b. Экран использует отрицательные значения для
оси, чтобы глубина росла вниз.

Есть ограничения именно визуализации: ambient series использует O.V вместо
фактического altitude surface; локальные начальные значения интерполяции и
ветвь continue могут сохранять не тот snapshot для соседних постоянных сегментов.
Поэтому картинки не являются эталоном тканевого состояния. Для нового планера
строить график из фактических snapshots и отдельно проверять интерполяцию.
Точная проверка legacy-графика: вызвать tissue graph handler на плане,
прочитать XYChart series и сравнить с snapshots/исходными кусочными формулами.

## Единицы и округления

F.G/H: L↔CuFt, множитель0.03531467. F.C/D:bar↔PSI,14.50377.
F.B: `rint(x*10)/10`, ties-to-even; F.J:HALF_UP на2 знака;
F.A(double,int):HALF_UP с заданным scale; Math.round(double) округляет как
floor(x+.5), в отличие от rint. На примере1.25 получаются1.2 против1.3.

Глубины в UI переключаются множителем3.3 и целочисленными округлениями, тогда
как разные формулы используют10.1325/33 либо10/32.5684678. Нельзя выбрать один
общий множитель и ожидать побитовой совместимости всех подсистем.

## Явные пробелы

- HTML/печать range tables и отрисованные chart series не проверены выполнением;
  численные ядра и snapshots проверены отдельно, способы проверки приведены выше.
- Редкие сочетания limits continuous blending разобраны по ветвям, но не имеют
  исчерпывающей runtime-матрицы. Для переноса нужны случаи для каждого условия
  i.A и проверка баланса O2/He/N2, включая нулевые знаменатели и два потока.
- Восстановленного расчёта резервов не найдено. Реализовать его по этим данным
  нельзя: нужна отдельная модель и её проверка.
